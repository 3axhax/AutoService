# Результат очистки companyId=3

Дата: 2026-11-02. Рабочая БД AutoService в /var/AutoService, отдельный PostgreSQL контейнер autoservice-prod-postgres_auto_service-1. Пользователь прямо запросил удаление всех смен/заказов компании3.

В одной транзакции удалены 4 orders,20 связанных ordersOptionValues и1 закрытая shifts; связанных additionalWorks было0. После удаления orders/shifts компании3 равны0. Параметры удалены явно перед orders, поскольку прямой SQL не вызывает Sequelize BeforeDestroy. Межфирменные связи повторно проверены и отсутствовали. TRUNCATE, изменение sequences, migrations и изменение кода не выполнялись.

Перед DML в REPEATABLE READ кратко взяты SHARE ROW EXCLUSIVE locks на public tables. Из экспортированного snapshot создан полный custom dump в защищённом игнорируемом server tmp/0005-company3-before-*.dump, права0600; pg_restore --list успешен, SHA-256 и журнал операции сохранены рядом в tmp/0005-company3-*.json. Запись приложения на время backup/транзакции ожидала освобождения locks; чтение и контейнеры продолжали работать.

До и после DML внутри транзакции сравнивались counts и отпечатки всех строк вне удаления во всех15 public tables. Они совпали; только после этого выполнен COMMIT. Проверены ожидаемые counts удалённых строк и отсутствие целевых записей. Поля пользователей, роли, цены, настройки и операционные данные остальных компаний не изменены.

Все8 контейнеров (3 AutoService и5 Analysis) сохранили id/image/StartedAt/restartCount; перезапусков не было. Локальная БД не изменялась. Дамп/персональные данные не выводились и не переносились в Git.

Первый проход остановился на чтении многострочного JSON аудита до backup и любых DELETE; транзакция откатилась. Парсер вывода исправлен на чтение до явного маркера. Повторный проход полностью выполнен, backup проверен, результат COMMIT подтверждён.

Откат после commit: по отдельному согласованному запросу восстановить backup в отдельную копию и выборочно вернуть удалённые orders/shifts/optionValues с проверкой ID/ссылок. Полное восстановление поверх работающей production БД может потерять более новые изменения, поэтому автоматически не выполняется. Проверенная резервная копия сохранена на сервере.
