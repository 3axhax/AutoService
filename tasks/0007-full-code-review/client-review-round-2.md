Дата: 2026-11-03. Проверено текущее рабочее дерево с незакоммиченными исправлениями первого ревью. Код приложения при повторном аудите не исправлялся.

## R2-1. [P1] После создания заказа или работы не обновляются список и итог смены

Код: `client/src/features/editOrderForm/ui/EditOrderForm.tsx:76–83`; аналогично `client/src/features/editAdditionalWorkForm/ui/EditAdditionalWorkForm.tsx:70–77`.

Новый guard `mounted.current` блокирует onSuccess после успешного создания. Fulfilled reducer выставляет active=false, React удаляет форму из OrderActiveList/AdditionalWorksActiveList, cleanup ставит mounted=false, и только затем выполняется `.then`. Обработчик, который должен перечитать сохранённые заказы/работы, уже не вызывается. Сами fulfilled reducers не добавляют ответ API в сохранённый список.

Воспроизведение: работник с открытой сменой → «Новый заказ» → заполнить → «Завершить». После успешного POST форма пропадает, но заказ отсутствует в таблице и общая сумма остаётся прежней. То же для дополнительных работ. Обновление страницы восстанавливает список, поэтому запись не потеряна в БД, но основной рабочий экран показывает неверный итог.

Подтверждение: браузер на временном изолированном Vite origin с реальными App/WorkerShift/формами и подменённым Axios adapter. Успешно созданы синтетические заказ и работа, каждый стоимостью 100. После обоих POST экран показывал итог 0 и пустые списки. Журнал запросов содержал только первоначальные GET и два POST; повторных fromActiveShift не было.

Направление исправления: обновлять списки/инвалидировать данные при успешной мутации независимо от жизненного цикла формы. Ограничение на callbacks старой сессии проверять по идентичности сессии, не по факту размонтирования формы, которая штатно исчезает после успеха.

## R2-2. [P1] Другая вкладка меняет токен запроса без смены пользователя и черновиков

Код: `client/src/shared/transport/RestAPI.ts:22–26,38–39`; восстановление store — `client/src/app/AppContainer.tsx:28–30`.

RestAPI перед каждым запросом читает токен из общего localStorage, а Redux пользователя и черновики живут отдельно в каждой вкладке. Обработчика события storage нет. Воспроизведение: вкладка 1 открыта под работником A и содержит его черновик; во вкладке 2 выйти и войти под B; в первой вкладке нажать «Завершить». Интерфейс первой вкладки всё ещё принадлежит A, но запрос уже отправляется с Bearer-токеном B. Backend создаст заказ от B в его компании/смене, если параметры совместимы. Если параметры несовместимы, новая серверная валидация может отклонить запрос, но смешение состояния и токена уже произошло.

Подтверждение: реальный Redux store восстановлен для синтетического A, создан черновик, localStorage заменён записью B (как при входе в другой вкладке), выполнен addOrder с подменённым API. В store остался A, тело содержало его черновик, Authorization содержал токен B. Секреты и реальная БД не использовались.

Направление исправления: привязать данные и токен запроса к одной сессии; синхронизировать смену сессии между вкладками и блокировать запись при несовпадении текущего store и сохранённой сессии.

## R2-3. [P2] Позднее закрытие смены очищает состояние следующей сессии через callback

Код: `client/src/features/shift/actionBlock/CloseShift.tsx:16–20`; защита в `client/src/shared/store/index.ts:60–62`.

Middleware игнорирует поздний fulfilled action для reducer, но возвращаемый thunk Promise всё равно содержит исходный успешный payload. Незащищённый `.then` в CloseShift после этого выполняет clearShiftsList/clearOrdersList/clearAdditionalWorksList уже для новой сессии. Воспроизведение: A подтверждает закрытие смены, запрос задерживается; A выходит, входит B, загружается его смена; приходит ответ A. Смена и списки B исчезают, хотя его смена на сервере по-прежнему открыта.

Подтверждение: реальный store, задержанный ответ closeActiveShift, logout, загрузка другой синтетической смены/списка и выполнение в точности callback CloseShift. После позднего ответа обе загруженные коллекции стали пустыми. Это новый эффект UI-состояния, а не серверное закрытие смены B.

Направление исправления: убрать дублирующую очистку из callback (актуальная успешная closeActiveShift уже обрабатывается root reducer) либо оградить callback сессией/requestId.

## R2-4. [P2] Экспорт выполняет скачивание после выхода из исходной сессии

Код: `client/src/entities/order/model/extraReducers.ts:130–136`.

downloadExcel вызывается внутри payload creator сразу после await. Проверка requestId в middleware происходит только при последующем fulfilled dispatch и уже не может остановить скачивание. Воспроизведение: A начинает экспорт → выходит, пока запрос выполняется → в той же вкладке входит B → приходит ответ A. Автоматически скачивается файл заказов A; смена сессии не ограждает этот побочный эффект.

Подтверждение: задержанный подменённый ответ экспорта, logout до ответа, mock browser download API. После logout зафиксирован вызов скачивания. Экспорт живых заказов не выполнялся.

Направление исправления: отменять экспорт при смене сессии и/или проверять актуальность сессии/requestId до downloadExcel, а не только при записи результата в Redux.
