# Серверное код-ревью — первый проход

Дата: 2026-11-03. Проверено текущее рабочее дерево, включая ранее добавленную проверку зависимостей цены. Исходники приложения в этом проходе не менялись. Найдены четыре P1 и два P2.

## S1 — P1: администратор компании получает компании и настройки других компаний

Места: `server/src/companies/companies.service.ts:12–13`, `server/src/companiesParametersOptions/companiesParametersOptions.service.ts:12–13` и соответствующие controllers.

GET /companies и GET /companiesParametersOptions требуют ADMIN, но контроллеры не передают текущего пользователя, а services выполняют findAll без where. Регистрация создаёт ADMIN своей новой компании с confirmed=true; отдельного системного администратора в проверке этих endpoints нет. Поэтому ограничение ADMIN не обеспечивает изоляцию арендаторов: обычный администратор может получить все компании и записи их доступных параметров, опций и зависимостей, а не только свои.

Подтверждение: настоящие services с подменёнными repository вызывают оба findAll с undefined options. Путь доступа проверен чтением RolesGuard/AuthService; реальные регистрации и чтение пользовательских данных не выполнялись.

Исправление: определять компанию из авторизованного пользователя и ограничивать запросы ею. Если нужен межкомпанейский обзор, выделить отдельное явно проверяемое системное полномочие, которое не выдаётся публичной регистрацией.

## S2 — P1: WORKER + MANAGER снимает ограничения компании в истории смен

Места: `server/src/shifts/shifts.service.ts:142–148`, `server/src/users/users.model.ts` (isOnlyWorker), `server/src/orders/orders.service.ts:105–110`.

RolesGuard допускает любой набор ролей, содержащий WORKER. Но isOnlyWorker=true только при ровно одной роли WORKER. У WORKER+MANAGER и isOnlyWorker, и isAdmin равны false; ShiftsService.getList формирует where только из дат, без companyId/userId. При отсутствии дат получается {}: доступны смены и агрегаты заказов/работ всех компаний. В edit заказа такой же пользователь обходит ветку ограничения текущей сменой/своим userId и может изменить чужой или закрытый заказ внутри своей компании. Это не проблема обычного единственного MANAGER: он не проходит RolesGuard; условие эксплуатации — сочетание ролей с WORKER и без ADMIN.

Подтверждение: настоящий RolesGuard с синтетическими session/user repositories допускает WORKER+MANAGER. Настоящий ShiftsService с таким user передаёт repository where={}. Расширение редактирования подтверждено кодом, отдельно HTTP-изменением не проверялось. Не проверялось, назначено ли такое сочетание кому-либо в текущей БД.

Исправление: всегда ограничивать companyId; полномочия определять явно и закрывать доступ по умолчанию. Все пользователи без ADMIN, которым разрешён endpoint работника, должны сохранять ограничения работника либо иметь явно описанную собственную политику.

## S3 — P1: неуспешное редактирование уничтожает прежние опции заказа

Места: `server/src/orders/orders.service.ts:117–125`, `server/src/orders/orders.model.ts:deleteOptions/saveOptions`.

Редактирование удаляет существующие ordersOptionValues, затем формирует и вставляет новые значения, затем обновляет суммы. Транзакции нет, а model helpers не принимают transaction. При ошибке форматирования, bulkCreate или последующего update уже выполненное удаление не откатывается. Пользователь получает ошибку сохранения, но исходное состояние заказа потеряно; суммы могут остаться прежними при отсутствующих или новых опциях. Аналогичный риск создания: AfterCreate вызывает saveOptions после вставки заказа без общей транзакции.

Подтверждение: настоящий OrdersService.edit с синтетическим existingOrder и ошибкой saveOptions. deleteOptions выполнен, update сумм не выполнен, Promise отклонён. Реальное удаление из БД не выполнялось. Входные данные orders/add/edit — Record, а не DTO; ошибочные структуры также могут доходить до формирования SQL-записей.

Исправление: полностью проверить/сформировать новые значения до удаления; удаление, вставку и суммы выполнять в единой транзакции с передачей transaction в model hooks/helpers. Проверить rollback при сбоях на каждом этапе, включая создание.

## S4 — P1: ID заказа или числовое поле подменяет условие доступности составной работы

Место: `server/src/price/price.service.ts:83–94` (validateCompositeParameters).

baseIds строится из всех скалярных чисел/числовых строк и ключей объектов param, без привязки к метаданным параметров. В набор попадают id заказа, числовой INPUT и произвольные поля тела. Валидация комбинации считает их выбранными опциями. Общий calculateOrderPrice, напротив, учитывает только реальные параметры с опциями: операция может пройти проверку, но не получить цену.

Подтверждение настоящим PriceService.calculateTotalValue с синтетическим справочником: car_type имеет опции 12/13, repair содержит опцию 30, её цена 100 требует [30,12]. Запрос id=12, car_type=13, repair=[{optionIds:[30],count:1}] принят и возвращает totalValue=0. Тот же запрос с id=999 отклоняется. Реальный заказ не создавался. Это подтверждает зависимость валидации от постороннего поля и бесплатное принятие недоступной операции в проверенном наборе цен.

Исправление: собирать базовые опции по типам/метаданным и положительным количествам, согласовать выбор опций в validator и pricing. Посторонние поля и INPUT не должны удовлетворять условиям цен. Добавить негативные тесты для id, числового ввода и нулевых количеств.

## S5 — P2: параллельное открытие создаёт несколько активных смен одного пользователя

Место: `server/src/shifts/shifts.service.ts:28–38`, модель shifts и миграции.

getOrCreateActiveShiftByUserCompany выполняет отдельные findOne и create. Два запроса /shifts/createActive либо добавления записей при отсутствии смены могут одновременно увидеть null и создать две активные смены. На уровне БД нет уникальности активной пары companyId/userId. Последующие findOne выбирают одну из них без определения порядка, из-за чего записи и отображаемые суммы могут распределяться между разными активными сменами. Клиентская блокировка не защищает от второй вкладки или параллельного API-запроса.

Подтверждение: два параллельных вызова настоящего service с repository, возвращающим null на поиск, создают две разные записи. Read-only запрос pg_indexes в локальной БД подтверждает, что у shifts есть только уникальный PK по id. Саму гонку в живой БД не запускали.

Исправление: обеспечить инвариант одной активной смены ограничением/частичным уникальным индексом и атомарной стратегией получения/создания с обработкой конфликта. Перед миграцией отдельно проверить и согласовать обработку существующих дублей. В этом ревью изменения схемы/данных не выполнялись.

## S6 — P2: Excel-экспорт теряет составные работы

Место: `server/src/orders/orders.service.ts:435–473` (downloadList).

Заголовки экспорта строятся по всем параметрам, включая COMPOSITE_LIST. Заполнение строк обрабатывает только INPUT/SELECT/SELECT_LIST/GRAPH_INPUT. Для составной работы не создаётся ячейка: выбранные материалы, метод и количество исчезают из Excel, хотя входят в итоговую стоимость заказа. Итоги при этом не пересчитываются и остаются, поэтому файл не объясняет состав суммы.

Подтверждение: настоящий downloadList с синтетическим заказом, содержащим COMPOSITE_LIST operation/count и подменённым DownloadExcelService. В data.header есть колонка repair, в data.rows[0] нет соответствующей ячейки. Файл с реальными заказами не создавался.

Исправление: форматировать составные операции по compositeOperationId с опциями/группами и количеством; проверить несколько операций одного параметра и соответствие суммы экспортируемым работам.
