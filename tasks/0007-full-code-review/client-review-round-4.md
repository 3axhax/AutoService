# Клиентское код-ревью — четвёртый проход

Дата: 2026-11-03. Область: текущее рабочее дерево после R3-исправлений. Новых правок приложения в этом проходе нет. Подтверждены четыре замечания: один P1, три P2.

## R4-1. [P1] Закрытие смены не исключает параллельное сохранение

Код: `client/src/entities/shifts/model/extraReducers.ts:46`; `client/src/entities/order/model/extraReducers.ts:31`; `client/src/features/shift/actionBlock/CloseShift.tsx:12–16`. Аналогичный независимый pending у additionalWorks.

closeActiveShift проверяет только shifts.pending, а addOrder/editOrder — только order.pending. Кнопки заказа/работы не блокируются при закрытии смены, а закрытие не ждёт записей. Поэтому закрытие смены и сохранение могут одновременно уйти на сервер. После принятого closeActiveShift root reducer очищает черновики/списки, middleware удаляет requestId всех записей смены; поздний успешный ответ сохранения затем отбрасывается.

Воспроизведение: заполнить заказ → подтвердить закрытие смены, задержав его HTTP-ответ → пока интерфейс ещё показывает смену, нажать «Завершить» заказа. Либо начать сохранение и закрыть смену до его ответа. В первом случае сохранение отправляется несмотря на shifts.pending=true; при ответе close раньше ответа save сохранённый заказ не попадает в интерфейс.

Подтверждение: настоящий store/thunk с подменённым API. Оба запроса отправлены одновременно, shifts.pending и order.pending стали true. После успешного close и затем успешного save ordersList остался пустым, черновик удалён.

Влияние на данные: по серверному алгоритму `getOrCreateActiveShiftByUserCompany` в OrdersService/AdditionalWorksService запрос сохранения, обработанный после фактического закрытия, может автоматически открыть новую смену. При другом порядке запись может завершиться уже для закрываемой смены. Это вывод из backend-контракта, а не эксперимент на живой БД. Клиент не контролирует принадлежность такой записи и скрывает её результат.

Направление исправления: единая взаимная блокировка закрытия и записей, включая thunk-проверки и UI; не удалять незавершённые операции до их однозначного результата. Серверную атомарность закрытия/записи проверить отдельно при backend review.

## R4-2. [P2] Позднее удаление загружает старый экран поверх новой истории

Код: `client/src/features/ordersListActionButton/OrdersListActionButton.tsx:22–24`; callback активной смены — `client/src/widgets/workerShift/ui/ClosedOrdersList/ClosedOrdersList.tsx:84–87`. Аналогично `client/src/widgets/workerShift/ui/ClosedAdditionalWorksList/AdditionalWorksListActionButton.tsx:27–30`.

После удаления `.then` вызывает onReload без проверки, что исходный список ещё открыт. Подтверждающее окно закрывается до завершения запроса, поэтому пользователь может перейти в историю. Поздний callback запускает fromActiveShift и становится последним запросом общего ресурса orders, вытесняя getByShiftId для открытой исторической смены.

Воспроизведение: удалить заказ текущей смены с задержкой ответа → перейти в историю и раскрыть другую смену → завершить delete → завершить запрос её заказов. Вместо её списка остаётся активный список; selector исторической смены показывает пусто. Повторного getByShiftId нет, поскольку id раскрытой смены не менялся. Поздний ответ предыдущей сессии способен аналогично вызвать ненужную загрузку новой сессии через этот callback — защита reducer не отменяет `.then`.

Подтверждение: реальный store; callback повторяет текущий обработчик ClosedOrdersList. Задержанный delete завершён после старта getByShiftId(5), callback загрузил пустой fromActiveShift, затем настоящий исторический ответ с записью shiftId=5 был проигнорирован. Итоговый selector смены 5 вернул пустой список. API/БД подменены.

Направление исправления: выполнять инвалидацию мутации с учётом текущего представления/сессии, а не через callback покинутого компонента. Не позволять старому экрану менять latest нового экрана.

## R4-3. [P2] Закрытый во время сохранения редактор оставляет устаревшие данные

Код: `client/src/features/editOrderForm/ui/EditOrderForm.tsx:76–83`; аналогично `client/src/features/editAdditionalWorkForm/ui/EditAdditionalWorkForm.tsx:70–77`.

«Отменить», Escape и закрытие окна доступны при pending. Это размонтирует форму и выставляет mounted=false. Сам HTTP-запрос не отменяется и может успешно сохраниться, но onSuccess уже не вызывается. Обработка editOrder.fulfilled/editAdditionalWork.fulfilled не обновляет сохранённые коллекции, а централизованное перечитывание middleware настроено только для add. Поэтому список остаётся старым даже после успешного сохранения.

Воспроизведение: открыть заказ ORIGINAL → изменить на UPDATED → нажать «Изменить» с задержкой ответа → закрыть окно → завершить успешный ответ. Таблица продолжает показывать ORIGINAL. Повторное открытие редактора тоже показывает ORIGINAL из старого ordersList. Следующее редактирование другого поля может отправить эти старые значения обратно и отменить предыдущую сохранённую правку.

Подтверждение: браузер с настоящими App/WorkerShift/редактором и подменённым Axios adapter. Сохранение UPDATED завершено после закрытия формы. В таблице и повторно открытой форме остался ORIGINAL; журнал запросов показал POST edit, но не последующий GET. Синтетические данные, без БД. Дополнительные работы имеют ту же ветку логики; отдельно в браузере проверялся заказ.

Направление исправления: результат редактирования должен обновлять/инвалидировать данные независимо от mounted формы с сохранением защиты сессий и текущего представления. Альтернатива — запрещать закрытие и повторное открытие до завершения записи, если это согласовано с UX.

## R4-4. [P2] Ответ об отсутствии активной смены оставляет прежнюю смену активной

Код: `client/src/entities/shifts/model/slice.ts:64–71`; потребитель — SelectWorkerActiveShift и WorkerShift.

getActiveShift.fulfilled обрабатывает только truthy payload. Когда API возвращает null, ранее загруженная active=true запись остаётся в shiftsList, и selector продолжает считать её текущей сменой.

Воспроизведение: загрузить активную смену A в истории → закрыть её в другой вкладке с той же сессией → вернуться на главную. Новый getActiveShift возвращает null, но интерфейс сохраняет A и кнопки «Новый заказ»/«Закончить смену» вместо «Начать смену». Смена токена не происходила, поэтому механизм синхронизации сессий здесь не помогает. Следующая запись может через серверный getOrCreate неявно открыть другую смену, пока клиент ещё показывает старую.

Подтверждение: реальный store, первый getActiveShift вернул {id:1,active:true}, следующий успешный getActiveShift вернул null. SelectWorkerActiveShift после второго ответа всё ещё вернул id=1. Закрытие в живой БД не выполнялось; контракт API null проверен по ShiftsService.

Направление исправления: null должен явно сбрасывать текущее активное состояние и связанные данные. Предпочтительно отделить активную смену от коллекции истории, чтобы историческая запись не определяла текущий рабочий режим.
