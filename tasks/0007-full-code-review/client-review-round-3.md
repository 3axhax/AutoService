# Клиентское код-ревью — третий проход

Дата: 2026-11-03. Проверено рабочее дерево после исправлений R2-1—R2-4. Код приложения не менялся. Найдены четыре замечания: один P1, три P2.

## R3-1. [P1] Создание во время первой загрузки скрывает существующие записи смены

Код: `client/src/shared/store/index.ts:103–112`; запись только нового заказа — `client/src/entities/order/model/slice.ts:58–61`, аналогично additionalWorks slice.

После успешного add middleware удаляет latest для fromActiveShift. Незавершённый ответ первоначальной загрузки затем полностью игнорируется. Fulfilled добавляет только новую запись; существующие записи, которые ещё не успели загрузиться, остаются неизвестны клиенту. Новый запрос вместо отброшенного не выполняется.

Воспроизведение: в смене уже есть заказ на 200; getActive и справочники загрузились, а первый GET orders/fromActiveShift задерживается. Работник создаёт заказ на 100 до его завершения. POST завершается, затем приходит исходный GET со старым заказом. Клиент оставляет только новый заказ и показывает 100 вместо 300. Аналогично теряются из отображения прежние дополнительные работы. Сами записи в БД не удаляются, но экран и итог смены неверны до повторной загрузки.

Подтверждение: реальный Redux store с подменённым API. Задержанный GET содержит запись id=1, успешный POST — id=2. После обоих ответов ordersList содержит только id=2. Отдельно воспроизведено для additionalWorksList. Живая БД не использовалась.

Причина пропуска тестами: нынешняя регрессия старого чтения использует пустой ответ. Она проверяет сохранность новой записи, но не сохранность ранее существовавших записей.

Направление исправления: после создания перечитывать актуальный список или объединять снимок с мутациями по версиям/идентификаторам. Нельзя молча отбрасывать единственный источник ранее существовавших записей без замены. Альтернатива — не разрешать запись до окончания обязательной первоначальной загрузки.

## R3-2. [P2] Отменённая подпись возвращается при следующем применении пустого canvas

Код: `client/src/features/editOrderForm/ui/GraphInput.tsx:20–30,50–59`.

signatureImg остаётся в GraphInput после отмены. SignatureInput при новом открытии монтируется с пустым canvas, но кнопка «Применить» использует старую signatureImg. Воспроизведение: открыть подпись → нарисовать линию → «Отменить» → снова открыть → не рисовать → «Применить». В заказ попадает именно отменённая подпись, которой в текущем canvas нет.

Подтверждение: браузер с настоящими GraphInput/SignatureInput/Modal. После отмены значение EMPTY; после повторного открытия и применения без рисунка значение APPLIED, появляется изображение ранее отменённой синтетической линии. Подпись реального человека и записи БД не использовались.

Направление исправления: держать буфер подписи на одно открытие, сбрасывать при отмене и синхронизировать с отображаемым canvas. Не применять скрыто сохранённый рисунок предыдущей попытки.

## R3-3. [P2] Перемонтирование SessionScope отменяет переход после входа

Код: `client/src/app/providers/index.tsx:12–14`; потерянный эффект — `client/src/features/loginForm/ui/LoginForm.tsx:34–39`.

Смена token перемонтирует InfoModalProvider вместе со всем дочерним деревом. LoginForm удаляется до того, как успевает отработать её effect с navigate('/'). Вход успешен, модалка закрывается вследствие перемонтирования, но URL и страница остаются прежними.

Воспроизведение: гость открывает /shiftsHistory → «Вход/Регистрация» → успешный вход администратором. Ожидаемый по LoginForm переход на / не выполняется; остаётся «Смены», а не административный список заказов. Та же структурная проблема есть у эффекта перехода RegistrationForm; регистрация отдельно не воспроизводилась. При входе со страницы 404 механизм также не переводит на главную.

Подтверждение: настоящий App/AppProvider/роутер в браузере с подменённым login API и синтетическими доступами. После успешного входа в меню показан Synthetic Admin, но URL остался /shiftsHistory и заголовок «Смены» сохранился. В БД вход не выполнялся.

Направление исправления: выполнить переход в компоненте, который переживает смену сессии, либо отделить сброс модального состояния от перемонтирования дерева, содержащего эффект перехода. Не полагаться на effect формы, которая удаляется тем же успешным входом.

## R3-4. [P2] Фильтр предлагает COMPOSITE_LIST без реализации выбора и API-контракта

Код: `client/src/entities/orderParameters/model/selectors.ts:135`, `client/src/features/ordersListFilters/ui/AddNewFilterParameterOptions.tsx:19–57`; применение пустого значения — `client/src/features/ordersListFilters/ui/AddNewFilter.tsx:28–58`.

В список фильтров включаются все параметры, в том числе COMPOSITE_LIST («Шиноремонт», добавленный существующей миграцией). Компонент выбора значения поддерживает только INPUT, SELECT, SELECT_LIST и GRAPH_INPUT. При выборе составного параметра поле отсутствует, однако filterValue с null формируется и кнопка «Добавить» разрешает его отправить. Backend orders.service.ts:603–642 тоже не содержит ветки COMPOSITE_LIST: такой фильтр не совпадает ни с одной строкой. В результате список и экспорт получают пустую выборку независимо от реально выполненных составных работ.

Подтверждение: вызов настоящего AddNewFilterParameterOptions с COMPOSITE_LIST возвращает div с children=null; прослежены формирование payload и серверный switch сопоставления фильтров. Наличие конкретных опций в текущей БД не проверялось. Сценарий относится к компании, где составной параметр включён в доступный справочник; такая возможность реализована в репозитории.

Направление исправления: исключить неподдерживаемые типы из предлагаемых фильтров до появления согласованного UI/API-контракта либо реализовать фильтрацию составных операций целиком.
