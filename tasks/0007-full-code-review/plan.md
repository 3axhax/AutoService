# Полное код-ревью проекта

Цель: выявить подтверждённые дефекты проекта. Первый этап — клиентская часть `client/`, с проверкой контрактов backend по необходимости.

Результат: отчёт с приоритетами, условиями воспроизведения и ссылками на код. Исправления поведения, API, БД и production в этот этап не входят.

Этапы: изучить клиентские потоки авторизации, заказов, смен, фильтров и экспорта; сверить API; выполнить доступные статические проверки и сборку; записать замечания и ограничения проверки.

Проверить риски потери данных, неверных цен, доступа и устаревшего состояния. Приёмка: каждое замечание подкреплено конкретным сценарием и кодом. Миграции и rollback не нужны, меняется только документация.

## 2026-11-03 — согласован этап исправлений

Проверки: регрессии на реальном Redux store с подменённым API, build/lint клиента и доступные UI smoke checks. Схема и данные БД не меняются, deploy не требуется. Rollback — возврат изменений кода через Git.

## 2026-11-03 — исправления серверного ревью S1–S6

Цель: изоляция компаний и прав работников, атомарная запись заказов, одинаковая семантика условий цены, безопасное открытие одной смены и полный Excel-экспорт. До исправления воспроизведения сохранены в server-review.md.

S1: передавать User из controllers в существующие services и фильтровать companyId. S2: WORKER без ADMIN сохраняет ограничения работника независимо от дополнительных ролей; companyId обязателен во всех ветках списка смен, edit/delete не получают undefined shiftId при отсутствии смены. S3: форматирование до удаления, транзакция создания/редактирования заказа и всех hooks/helpers опций, блокировка строки при edit. S4: собирать условия только из объявленных SELECT/SELECT_LIST и положительных количеств, согласовать валидатор зависимостей. S5: pg_advisory_xact_lock(companyId,userId) перед find/create в транзакции, поддержать внешнюю транзакцию заказа. S6: экспортировать составные операции отдельными строками ячейки с опциями и количеством.

Решение по S5 уточнено до реализации: используем транзакционную advisory-блокировку вместо частичного уникального индекса. Она действует между процессами сервера на существующем пути открытия смен, не требует DDL и обработки старых дублей. Read-only аудит ранее подтвердил отсутствие уникального индекса. Старые дубли не объединяем/не удаляем. Схема, persistent данные, env и роли пользователей не меняются, применение миграции не требуется.

Проверки: регрессии изоляции и смешанных ролей, rollback/hooks, конкурентного открытия, отрицательных условий цены и экспорта; серверные build/tests; клиентские регрессии/build; HTTP negative auth без записи в БД. Настоящие операции записи не выполнять на текущей БД: транзакции и конкуренцию проверять на изолированных repositories/моделях. Для интеграционной проверки БД использовать изолированную временную БД только при возможности безопасного запуска без воздействия на текущие данные. Откат — вернуть относящиеся к этапу файлы сервера; миграций нет. Форматы успешных API-ответов сохраняются. Риски: все writers открытия смен должны использовать существующий service; внешний SQL не защищён advisory-протоколом.
