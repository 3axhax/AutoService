# Код-ревью клиентской части

Дата: 2026-11-03. Область: `client/src`, конфигурация клиента, общий расчёт цены и необходимые контракты backend. Это первый этап полного код-ревью проекта; backend целиком пока не проверен. Поведение приложения не изменялось.

Приоритеты: P1 — исправить в первую очередь (разделение пользователей, поломка основного сценария); P2 — функциональные дефекты, которые нужно исправить планово.

## 1. [P1] Данные и черновики пользователя переживают выход

Код: `client/src/pages/logout/LogoutPage.tsx:13–16`, `client/src/entities/user/model/slice.ts:71–78`, `client/src/shared/store/index.ts`.

Выход очищает только user и список смен. `order.ordersValue`, `additionalWorks.additionalWorksValue`, списки заказов/работ, справочники и пользователи остаются в общем store. Воспроизведение: работник A заполняет черновик → выходит → работник B входит в той же вкладке → открывает свою смену. Активные черновики A отображаются у B; отправка оформляет их от B в его компании/смене. Также при ошибке обновления списка могут остаться данные A. Завершение смены тоже не удаляет черновики: они переходят в следующую смену.

Проверка: на реальном Redux store создан черновик с обезличенным значением, выполнен `logoutUser`, подтверждено сохранение значения. Путь отображения проверен через `activeOrdersListSelect` и `OrderActiveList`.

Исправление: сбрасывать состояние, привязанное к пользователю/компании, при смене сессии; обработать незавершённые запросы предыдущей сессии. Отдельно определить судьбу черновиков при закрытии смены.

## 2. [P1] Список работников перестаёт загружаться и становится undefined

Код: `client/src/entities/users/model/slice.ts:23–24,53–55`; потребитель — `client/src/entities/orderParameters/model/selectors.ts:115–116`.

В `finally` вызван `setPending(false)` без dispatch. После первого запроса pending навсегда true. Повторный `getUsersList` пропускает запрос, но завершается fulfilled с undefined; reducer записывает undefined вместо массива. При открытии фильтра работников `.filter` вызывает исключение. Сценарий: загрузить страницу администратора, выйти и снова войти без перезагрузки вкладки; повторный mount `OrdersPage` вызывает этот thunk. После ошибки первого запроса повторной загрузки также нет.

Проверка: два последовательных dispatch с подменённым Axios adapter; выполнен один запрос, pending=true, users=undefined.

Исправление: dispatch сброса pending, безопасная обработка пропущенных запросов и fulfilled payload; сброс при смене пользователя.

## 3. [P2] Ошибка сохранения вызывает обработчик успеха и закрывает редактор

Код: `client/src/features/editOrderForm/ui/EditOrderForm.tsx:62–68`; аналогично `client/src/features/editAdditionalWorkForm/ui/EditAdditionalWorkForm.tsx:65–78`. Закрытие — `client/src/features/ordersListActionButton/OrdersListActionButton.tsx:44–49` и `client/src/widgets/workerShift/ui/ClosedAdditionalWorksList/AdditionalWorksListActionButton.tsx`.

`dispatch(createAsyncThunk(...))` возвращает разрешённый Promise и при rejected action. `.then` без проверки результата вызывает onSuccess после HTTP 400/403/500 или сетевого сбоя. В режиме редактирования запускается перечитывание списка и закрывается окно, хотя изменения не записаны; ошибка исчезает из поля зрения. Для заказов этот reload также очищает order.error через pending matcher.

Воспроизведение: изменить существующий заказ/работу, обеспечить отказ POST сохранения, нажать «Изменить». Редактор должен остаться открыт и показать ошибку.

Исправление: проверять fulfilled action и успешный payload либо использовать unwrap с обработкой ошибки; пропущенный из-за pending запрос тоже не считать успехом.

## 4. [P2] Быстрые переходы и фильтры теряют последний запрос

Код: `client/src/entities/order/model/extraReducers.ts:106–129`, `client/src/entities/order/model/slice.ts:110–116`; аналогичный паттерн — shifts и просмотр содержимого смен.

Общий pending молча отбрасывает новый запрос. UI уже меняет currentPage/filters. Если во время загрузки страницы 1 выбрать страницу 2, запрос страницы 2 не отправится, а ответ страницы 1 будет отклонён проверкой currentPage. Автоматического повтора нет: таблица остаётся пустой или со старыми строками при новом номере страницы. При изменении фильтра на той же странице старый ответ принимается, потому что сравнивается только currentPage. В истории смен быстрый выбор другой смены аналогично может оставить раскрытую смену без деталей.

Проверка: Axios adapter задержал ответ страницы 1, затем выполнены setCurrentPage(2) и повторный thunk. Второй payload=undefined; после первого ответа актуальная страница=2, данные не обновлены.

Исправление: разрешить актуальный запрос с requestId/ключом фильтров и страницы, отменять или игнорировать устаревший ответ; не терять последнее намерение пользователя.

## 5. [P2] Отмена редактирования сохраняет изменения в черновике

Код: `client/src/entities/order/model/reducers.ts:28–45`, `client/src/entities/orderParameters/model/selectors.ts:28–34`; аналогично additionalWorks. Закрытие modal сбрасывает только open/onAccess (`client/src/app/providers/infoModalProvider/InfoModalProvider.tsx:43–46`).

Редактирование сразу пишет в глобальный ordersValue. Отмена окна не удаляет этот буфер, а selector всегда предпочитает его свежему ordersList. Сценарий: поменять номер автомобиля → «Отменить» → снова открыть заказ. Отменённый номер снова показан. Если затем изменить другой параметр и сохранить, отменённый номер тоже уйдёт на сервер. Перечитывание списка после успешного сохранения также не обновляет старый буфер; данные, изменённые другой сессией, могут быть перезаписаны при следующем редактировании.

Исправление: отделить буфер конкретного открытия редактора, удалять при отмене и успешном сохранении, заново инициализировать из актуальной записи.

## 6. [P2] Смена родительской опции оставляет несовместимые значения в заказе

Код: `client/src/entities/order/model/reducers.ts:44–45`, `client/src/entities/orderParameters/model/selectors.ts:78–107`, `client/src/entities/order/model/extraReducers.ts:40–45,63–66`.

Зависимости фильтруют видимые параметры/опции, но не очищают ранее выбранные значения. Воспроизведение на конфигурации зависимостей из репозитория: выбрать car_type=12 и wheel_diameter=18, затем car_type=13, для которого допустимы только 14–17. Значение 18 остаётся в ordersValue и отправляется при сохранении, хотя в форме его уже нельзя выбрать. Аналогично скрытые поля юрлица остаются при переключении типа клиента. Общий калькулятор получает значения без применения этих UI-зависимостей, поэтому несовместимые работы/опции способны влиять и на сумму.

Проверка: прослежены reducer, selector, payload и калькулятор; пример соответствует `companiesParametersOptions.initialData.ts`, но наличие именно такой конфигурации в текущей БД не проверялось — initialData не обновляет существующие строки.

Исправление: при смене родителя нормализовать зависимые значения, включая составные операции; проверять допустимость на сервере. До подтверждения валидности не отправлять скрытые несовместимые значения.

## 7. [P2] Очистка незавершённого диапазона оставляет невидимый фильтр

Код: `client/src/shared/ui/DateSelectInterval.tsx:42–47`; потребители — FiltersList и WorkerShiftsHistoryFilters.

clearDate уведомляет родителя только если заданы обе границы. Сценарий: применить диапазон A–B → выбрать первую дату нового диапазона C (end=null) → нажать крестик. Локальные даты очищаются, но родитель сохраняет A–B и новый запрос без фильтра не отправляется. Пользователь видит пустой календарный фильтр, хотя список и экспорт заказов продолжают использовать старые ограничения.

Исправление: при очистке всегда уведомлять родителя `[null,null]`; синхронизировать отображение с применённым фильтром.

## 8. [P2] Единственный административный пункт «Объекты» ведёт на 404

Код: `client/src/widgets/navigation/ui/Navigation.tsx:23–27`, `client/src/app/AppContainer.tsx:45–71`.

Для администратора отображается ссылка `/facility`, но такой маршрут отсутствует: роутер отправляет её на NotFoundPage. Воспроизведение: войти администратором → нажать «Объекты».

Исправление: согласовать пункт меню с реально реализованной страницей и маршрутом.

## 9. [P2] Фильтр «Подпись: Нет» отправляет несовместимое с API значение

Код: `client/src/features/ordersListFilters/ui/AddNewFilterParameterOptions.tsx:43–53`; контракт — `server/src/orders/orders.service.ts:603–631`.

RadioGroup отправляет 0 для «Нет». Backend распознаёт отсутствие GRAPH_INPUT только при filterValue=null; ветка наличия требует значение >0. Ноль не проходит ни одну ветку, поэтому такой фильтр возвращает пустой список даже при наличии заказов без подписи. Сценарий: добавить фильтр подписи, явно выбрать «Есть», затем «Нет» и применить. Для воспроизведения важно именно выбрать «Нет»: первоначальный value=null тоже визуально отображается как «Нет», но отправляет другое значение.

Проверка: сопоставлены значения компонента, payload AddNewFilter и оба условия backend. Та же несовместимость затрагивает экспорт с этим фильтром.

Исправление: согласовать представление отсутствия подписи между UI, типом фильтра и API; исключить два разных значения у одинаково отображаемого выбора.

## Проверки и ограничения

- Изучены клиентские entities, страницы, формы, widgets, shared transport/UI, конфигурация и нужные контракты backend. Полный аудит backend, production и зависимостей на уязвимости не входил в этот этап.
- Локальный `npm run build`: успешно, TypeScript и Vite. Предупреждения: локальный npm использует Node 18.16 ниже требования Vite; два некорректных CSS var; JS chunk около 737 kB. Это дополнительные замечания, не включённые в девять функциональных дефектов.
- Локальный `npm run lint`: успешно.
- Выполнены изолированные проверки реального Redux store с подменённым Axios adapter: повторный users load, сохранение черновика после выхода, потеря запроса пагинации, приоритет старого черновика над обновлённой записью и вызов then после rejected сохранения. Дополнительно подтверждено исключение selector при отсутствующем заказе; без установленного обычного пользовательского сценария оно не включено отдельным дефектом.
- Проверки не обращались к БД и не создавали заказов/смен. Полный браузерный smoke test и проверка живого API не выполнялись; пользовательские сценарии выше выведены из кода, где не указан runtime-тест.
- Docker Compose показал три работающих контейнера, PostgreSQL healthy. Контейнерные build/lint запущены отдельно; итог ниже фиксируется после завершения.
- Файлы приложения не менялись; исправления замечаний требуют отдельного этапа.
