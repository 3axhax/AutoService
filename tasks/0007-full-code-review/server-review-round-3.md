# Серверное ревью — третий проход

Дата: 2026-11-03. Проверено рабочее дерево после исправлений SR2-1–SR2-3. Новых регрессий в исправленных сценариях не подтверждено; найдены один P1 и три P2 в смежных потоках. Исходники приложения этим проходом не менялись.

## SR3-1 — P1: выход не отзывает действующую серверную сессию

Места: `server/src/users/usersSessions/usersSessions.service.ts:18–22`, `server/src/auth/auth.controller.ts`; клиентский путь — `client/src/pages/logout/LogoutPage.tsx` и logoutUser в user slice.

Выход очищает только localStorage/Redux и навигацию. Серверного endpoint отзыва сессии нет, строки users-sessions не удаляются и не помечаются недействительными. checkUser проверяет только совпадение token, без срока действия; RolesGuard принимает найденную сессию. Поэтому сохранённая до выхода копия Bearer продолжает давать доступ к защищённым методам, в том числе после того, как пользователь завершил работу. Новый вход не отзывает старые сессии. Это не обход проверки пароля и не утверждение о наличии утечки токена, но выход не прекращает полномочия уже выданного токена.

Подтверждение: чтение полного клиентского пути logout и доступных auth endpoints; настоящий UsersSessionsService/RolesGuard с синтетическим repository продолжает принимать сохранённый токен. Удаление локального состояния не вызывает серверных действий. Реальных токенов и сессий пользователей не читали/не отзывали, полный браузерный logout с реальной БД не выполняли.

Исправление: защищённый endpoint отзыва текущей сессии и вызов его при выходе с сохранением возможности очистить локальную сессию при сетевом сбое. Проверить повторный запрос отозванным токеном и политику ошибок/других сессий. Срок жизни сессий можно определить отдельно; это не заменяет отзыв при успешном выходе.

## SR3-2 — P2: параллельная регистрация создаёт пользователей с одинаковым email

Места: `server/src/auth/auth.service.ts:52–61`, `server/src/users/users.model.ts:email`, `server/src/users/users.service.ts:getUserByEmail`.

Проверка существования email — отдельный SELECT перед созданием. У users.email нет уникальности в модели и локальной БД; два запроса могут одновременно получить null и оба создать пользователя/компанию/сессию. getUserByEmail затем использует findOne, поэтому email перестаёт однозначно определять учётную запись: вход может выбрать не того из двух пользователей и отказать с правильным для второго паролем. Rate limit по IP не обеспечивает уникальность между разными IP/процессами.

Подтверждение: два параллельных вызова настоящего AuthService.register с синтетическими repositories, в которых оба предварительных чтения возвращают null, успешно создали два разных user id и две компании для одной строки email. Read-only pg_indexes текущей локальной БД показал только users_pkey по id, индекса уникальности email нет. Реальные регистрации и гонка вставок в БД не выполнялись.

Исправление: определить нормализацию email, обеспечить уникальность на уровне БД и преобразовывать конфликт в 409. До миграции выполнить read-only аудит существующих дублей и согласовать их обработку; не удалять/объединять пользователей автоматически.

## SR3-3 — P2: ошибка регистрации оставляет частично выполненную регистрацию

Место: `server/src/auth/auth.service.ts:58–88`, `server/src/users/users.service.ts:createUser`.

Компания, пользователь, связь с ролью и сессия создаются последовательными независимыми записями. Общей transaction нет. Сбой создания сессии возвращает 400, хотя компания и учётная запись уже созданы; повтор того же запроса возвращает 409. При более раннем сбое привязки роли пользователь тоже уже записан, но может остаться без ролей. При сбое создания пользователя остаётся компания. Пользователь видит отказ, а backend сохраняет частичный результат.

Подтверждение: настоящий AuthService с синтетическим persisted-user repository и искусственным отказом createSession: первый register завершился 400, persisted-user остался, повтор завершился 409. Роль/компания при этом не откатываются по коду. Сбой роли отдельно на БД не воспроизводился. При позднем сбое сессии пользователь потенциально может восстановиться обычным входом — это не гарантированная потеря доступа во всех случаях.

Исправление: company/user/users-roles/session в одной transaction с передачей её всем service/model writes и контролируемым rollback. Сохранить обработку уникальности email и проверить сбой каждого этапа, затем успешный повтор.

## SR3-4 — P2: обрезка ID составных операций сливает разные операции

Места: `server/src/orders/orders.service.ts:243–247`, `server/src/price/normalize-order-input.ts:COMPOSITE_LIST`, `server/src/orders/format-composite-export.ts`.

Входной validator не проверяет длину/уникальность operation.id. Formatter молча обрезает переданный id до 64 символов. Два разных ID с одинаковым 64-символьным префиксом сохраняются как одна группа compositeOperationId. Дубликаты коротких ID также разрешены. Экспорт и восстановление редактора группируют по этому полю: выбранные опции объединяются, количество берётся от первой строки вместо сохранения отдельных операций. Следующее редактирование может дополнительно получить повторяющиеся optionIds одной группы.

Подтверждение настоящими PriceService.prepareOrder, OrdersService._formatParamToOptions и formatCompositeExport с синтетическими метаданными: две операции с уникальными ID ('a' × 64 + '1' / '2'), optionIds=[30], counts=1/3 и ценой 100 проходят проверку с общей суммой 400. Formatter даёт обеим одинаковый compositeOperationId. Экспорт получает одну строку «1. Repair + Repair × 1». Клиентский редактор отдельно браузером не проверялся; его группировка подтверждена чтением formatOrderValueFromOrderItemList.

Исправление: проверять допустимую длину и уникальность ID внутри параметра либо генерировать серверные уникальные ID без потери идентичности. Не обрезать молча; предусмотреть конфликт отсутствующих/явно заданных ID и проверить round trip save → read/edit → export для нескольких операций.
