## SR4-1 — P2: допустимые DTO пропускают filters, после чего список заказов падает

Места: `server/src/orders/dto/orders.dto.ts:26–27`, `server/src/orders/orders.service.ts:343–345`; аналогичный доступ к filters есть в downloadList.

filters отмечен @IsOptional, но не имеет значения по умолчанию и проверки массива/вложенных элементов. {} и filters:null проходят глобальный ValidationPipe. Затем getForAdmin без проверки вызывает param.filters.filter и выбрасывает TypeError вместо нормального ответа или 400. filters:{} также проходит DTO и падает, поскольку .filter не является функцией. Вложенные null/неверные элементы тоже не проверяются. Такой же DTO используется для Excel-экспорта, который рассчитывает на массив фильтров.

Подтверждение: настоящий ValidationPipe с transform=true, whitelist=true, forbidNonWhitelisted=false и настоящий GetOrdersListDto приняли {}, {filters:null}, {filters:{}}. Каждый результат передан настоящему OrdersService.getForAdmin с синтетическим авторизованным user; во всех случаях получен TypeError до обращения к repository. В штатном Nest это необработанная ошибка 500. Живой авторизованный endpoint и Excel с данными не вызывались; клиент обычно отправляет массив и потому текущими UI-регрессиями случай не покрыт.

Исправление: определить контракт отсутствующих фильтров (например, []), проверить массив и DTO вложенных элементов, согласовать getForAdmin/downloadList. Отсутствующее необязательное поле не должно приводить к 500; неверная структура должна отклоняться до service. Добавить HTTP-проверки отсутствия, null, объекта, неверных элементов и корректного пустого массива.

## SR4-2 — P2: преобразование суммы дополнительной работы скрывает ошибку и меняет значение

Место: `server/src/additionalWorks/dto/additionalWorks.dto.ts:9–15`, наследуется EditAdditionalWorkDto.

Transform использует parseInt и заменяет NaN на 0 перед @IsNumber. Поэтому непустая нечисловая строка превращается в валидный ноль, частично числовая строка принимается частично, а дробная сумма молча теряет дробную часть. Валидация проверяет уже подменённое значение, и services сохраняют его как успешную операцию. Это не просто сообщение об ошибке: значение денег в записи отличается от запроса.

Подтверждение: настоящий глобальный ValidationPipe и AddNewAdditionalWorkDto, затем настоящий AdditionalWorksService.addNew с изолированными withActiveShift/repository: totalValue='not-a-number' принят и передан create как 0; '125.75' как 125; '100junk' как 100. Реальных записей не было. Сумма модели хранится во FLOAT, @IsNumber не требует целого, поэтому молчаливое truncation не следует из объявленного типа. Даже при намеренной политике целых рублей неправильный формат следует отклонять, а не превращать в другую сумму.

Исправление: строгий разбор всего значения с конечным числом, явная политика пустого/отсутствующего поля; некорректные строки отклонять 400. Для дробных сумм либо сохранять поддержанную точность, либо явно запрещать, не обрезая молча. Проверить add/edit, числовую JSON-сумму и строку из клиентского number input.
