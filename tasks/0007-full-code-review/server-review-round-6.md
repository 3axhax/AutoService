# Шестое серверное ревью — 2026-11-03

## SR6-1 — P2: служебные фильтры принимают значения, непригодные для запроса

Место: server/src/orders/orders.service.ts:712–727, 742–743; OrderFilterItem в server/src/orders/dto/orders.dto.ts.

DTO проверяет общую форму filterValue (string | finite number | null), но значения служебных фильтров не проверяются по назначению. Например, filters=[{filterName:'userId',filterValue:'not-an-id'}] проходит настоящий ValidationPipe; _formatUserCondition создаёт id:NaN. Настоящий Sequelize query generator выдаёт условие id = NaN; PostgreSQL трактует NaN как имя колонки и возвращает ошибку, которая на list/export становится 500. Неверная дата начала при корректной дате конца также проходит DTO: parseDateFromFormat возвращает undefined, Sequelize строит createdAt >= NULL, и отчёт молча становится пустым.

Подтверждение: изолированный сценарий настоящих ValidationPipe/GetOrdersListDto/OrdersService и PostgreSQL query generator. Синтетический SELECT 1 WHERE 1 = NaN в локальном PostgreSQL, внутри BEGIN READ ONLY, подтвердил ошибку column "nan" does not exist. Сессия psql завершилась, записи и пользовательские данные не затрагивались. Путь настоящего HTTP с repository рабочей БД не запускался; 500 следует из необработанной ошибки запроса, а не из измеренного HTTP-ответа.

Рекомендация: до запросов проверять userId как положительный целый ID, даты как корректные календарные значения согласованного формата; отклонять ошибочные значения 400. Общую поддержку null для GRAPH_INPUT сохранить. Проверить одинаковое поведение list/export.

## SR6-2 — P2: верхняя граница дня исключает последнюю дробную секунду

Место: server/src/utils/parseDateFromFormat.ts:16–19. Используется заказами (список/Excel) и GetShiftListDto для истории смен.

При end=true парсер устанавливает 23:59:59, оставляя миллисекунды равными 0. Запросы используют <= этой даты. Поэтому заказ, созданный в 23:59:59.500, или смена, закрытая в это время, отсутствуют в отчёте за соответствующий день. createdAt/closedAt сохраняют дробные секунды, поэтому это потеря записей на границе корректного интервала.

Подтверждение: настоящий ValidationPipe и DTO для заказов/смен, затем реальные _formatCreatedAtCondition и _formatIntervalWhereProps. Для даты 03.11.2026 обе верхние границы имеют getMilliseconds()=0; синтетическая запись того же дня 23:59:59.500 не удовлетворяет условию <=. Рабочие записи не создавались и не просматривались.

Рекомендация: использовать полуоткрытый интервал с условием < начала следующего календарного дня; это сохраняет и точность PostgreSQL выше миллисекунд. Добавить проверки дробной последней секунды, полуночи следующего дня и одинакового поведения списка, Excel и истории смен.
