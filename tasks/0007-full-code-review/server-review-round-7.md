# Седьмое серверное ревью — 2026-11-03

## SR7-1 — P2: сумма зависит от порядка одинакового набора тарифов

Место: packages/pricing/src/calculate-order-price.ts:26–34; серверный вызов через PriceService.prepareOrder/calculateTotalValue.

getMatchingPrices удаляет ранее добавленный общий тариф при встрече более специфичного. Обратный порядок не обработан: если специфичный тариф уже добавлен, следующий общий тоже добавляется, и sumPrices суммирует оба для одного mainOptionId. PriceService.getAll не задаёт порядок findAll; правильность суммы не должна зависеть от физического порядка строк. Это касается обычных и составных операций, использующих общий helper; сервер сохраняет полученные суммы заказа. Пакет также используется клиентом.

Подтверждение настоящим PriceService с синтетическими repositories: выбраны vehicleType=1 и works={10:2}; тариф mainOptionId=10, value=400, conditions=[10] и его уточнение value=550, conditions=[10,1]. Порядок общий→уточнённый даёт 1100, обратный порядок того же набора — 1900. Ожидается 1100 в обоих случаях: существующий тест пакета прямо проверяет замену менее специфичного тарифа, но только в одном порядке.

Условие проявления — наличие совместимых общих/уточнённых тарифов для одной основной опции. В initialData-снимке таких пар не найдено; наличие в действующей БД не проверялось, утверждения о текущих неверных суммах нет. Сценарий поддерживается кодом/тестами пакета и не должен требовать определённого порядка БД.

Рекомендация: выбирать подходящие недоминируемые по условиям тарифы независимо от порядка, сохранив существующую политику для разных mainOptionId. Проверить перестановки общего/уточнённого тарифов и нескольких уровней условий, обычные и составные операции, quantity/discount и одинаковые результаты клиента/сервера. Сортировка SQL сама по себе не исправляет общий алгоритм.

## SR7-2 — P2: удаление одной записи принимает массив ID и удаляет несколько

Место: server/src/orders/orders.controller.ts:58 и server/src/additionalWorks/additionalWorks.controller.ts:52; передача id в where методов delete соответствующих services.

Тело типизировано inline как {id:number}, поэтому runtime metadata — Object и глобальный ValidationPipe не проверяет ID. Запрос {id:[71,72]} проходит и передаёт массив Sequelize. Sequelize трактует where.id=[71,72] как IN (71,72), а не как ошибочный scalar ID. OrdersService выбирает первую запись для блокировки смены, затем destroy удаляет все подходящие ID этой смены. AdditionalWorksService также удаляет все ID текущей смены. Оба возвращают true, маскируя массовое удаление под успешное удаление одной записи. Ограничения компании/владельца/смены сохраняются; обхода tenant-изоляции в этом сценарии не обнаружено.

Подтверждение: настоящий ValidationPipe с metatype Object, затем реальные controllers/services с изолированными repositories и синтетическими сменами. Один вызов каждого delete с id=[71,72] удалил две синтетические записи и вернул true. Настоящий PostgreSQL query generator Sequelize подтвердил предикат id IN (71,72) с сохранёнными ограничениями компании/смены/пользователя. Реальные DELETE и HTTP-запросы записи в рабочую БД не выполнялись.

Рекомендация: применить DTO scalar ID с проверкой положительного целого и строгим преобразованием, отклоняя array/object/null/missing/дробные значения до вызова service. Добавить HTTP-регрессии обоих маршрутов: массив даёт 400 без destroy, корректный ID удаляет ровно одну запись, чужая компания/смена остаются защищены.
