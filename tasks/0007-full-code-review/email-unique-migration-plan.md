# План применения уникальности email — выполнено локально

Дата: 2026-11-03. Только локальная БД AutoService; production не затрагивается.

## Готовое изменение

Модуль: `server/src/migrations/migrations.email-unique.ts`, функция `applyEmailUniqueness`. Не подключена к startup migrations и не применялась.

Нормализация идентичности email: trim + lower case. Приложение уже использует эту нормализацию при регистрации/входе и транзакционный lock нормализованного email при регистрации. Ограничение БД дополнительно защищает от любых иных writers.

Основной DDL:

```sql
CREATE UNIQUE INDEX IF NOT EXISTS users_email_normalized_unique
ON users (lower(btrim(email)));
```

Функция в одной транзакции берёт migration lock, проверяет число групп дублей, создаёт индекс и записывает `add_users_normalized_email_unique` в таблицу migrations с ON CONFLICT DO NOTHING. При найденных дублях прекращает работу, не удаляет и не объединяет учётные записи. Существующие email не перезаписываются.

## Предварительный аудит

Read-only запрос количества групп `lower(btrim(email))` с COUNT(*) > 1 вернул 0 в локальной БД. Адреса и пользовательские данные не выводились. Перед применением аудит повторить.

## Порядок после разрешения

1. Создать consistent custom-format backup локальной БД через pg_dump в игнорируемом `tmp/backups/`. Не выводить содержимое, credentials или строки данных, не помещать backup в tasks/Git.
2. Проверить успешный exit pg_dump, читаемость каталога pg_restore и, в изолированной временной БД, возможность восстановления и ожидаемые агрегаты/схему. Текущую БД при проверке не восстанавливать и не перезаписывать.
3. Повторить аудит дублей. При ненулевом результате остановиться и согласовать разбор; ничего не объединять автоматически.
4. Выполнить подготовленную функцию миграции для локальной БД. Не запускать весь комплект старых миграций ради индекса.
5. Read-only проверить валидный unique-индекс и отметку migrations, повторяемость запуска. Не создавать реальных тестовых пользователей в текущей БД.
6. После одобренного применения подключить тот же идемпотентный шаг к штатному migration workflow для последующих согласованных поставок. Production-поставка требует отдельного поручения пользователя.

## Риски и откат

Обычное создание индекса может кратковременно блокировать запись users; объём и состояние БД проверить перед применением. При конфликте уникальности транзакция откатывается целиком. При необходимости отката отдельно согласовать DROP INDEX users_email_normalized_unique и удаление только соответствующей отметки migrations. Данные пользователей менять не требуется; приложение сохраняет защиту транзакционным email-lock. Не использовать reset/clean/down -v и не трогать pgdata.

## Состояние до разрешения

Модуль покрыт изолированными тестами повторяемости, записи отметки в transaction и остановки при дублях. Реальный DDL, backup и восстановление ещё не выполнялись: ожидается разрешение по tasks/README.md:63–65.
