Дата: 2026-11-03. Проверено текущее рабочее дерево после R4-исправлений. Новых правок приложения нет. Подтверждены три замечания P2.

## R5-1. [P2] Ошибка перечитывания после сохранения скрывает рассинхронизацию данных

Код: `client/src/features/ordersListActionButton/OrdersListActionButton.tsx:14–16`, `client/src/pages/orders/OrdersPage.tsx:18–30`, `client/src/entities/order/model/reducers.ts:11–16`. Перечитывание после мутации — shared/store/index.ts; read rejected сбрасывает loading в order slice.

После успешного POST edit store запускает GET списка. Если GET завершается ошибкой, loading становится false, но в ordersList остаются прежние значения. Форма закрывается по успешному результату POST. OrdersPage показывает только ошибку справочника параметров, а не order.error, поэтому ошибки обновления списка на экране нет. Кнопка «Редактировать» снова доступна. beginEditOrder дополнительно стирает error и копирует старую запись в новый буфер.

Воспроизведение: заказ ORIGINAL → изменить на UPDATED → API edit отвечает успехом → следующий getForAdmin отвечает ошибкой/сеть пропадает. Таблица показывает ORIGINAL без уведомления о сбое. Повторно открытый редактор тоже показывает ORIGINAL. При следующем изменении другого параметра весь старый буфер может уйти на сервер и отменить уже сохранённую правку. Аналогичную обработку read error следует проверить для активного списка и дополнительных работ.

Подтверждение: на реальном store после успешного edit и ошибочного перечитывания loading=false, order.error непустой, ordersList содержит ORIGINAL. После beginEditOrder буфер содержит ORIGINAL, error снова пустой. Браузер с настоящими App/формами и подменённым API подтвердил отсутствие ошибки на странице, доступность кнопки и старое значение в повторно открытой форме. Живая БД не использовалась; последствия следующей перезаписи выведены из полной отправки буфера в edit API.

Направление исправления: различать подтверждённую запись и неуспешную синхронизацию списка. Показывать ошибку и возможность повторить чтение; не разрешать незаметно использовать устаревшую запись как свежую основу редактора. Не выдавать ошибку GET за отказ уже выполненной записи.

## R5-2. [P2] Удаление последней строки страницы оставляет недоступную пустую страницу

Код: `client/src/entities/order/model/slice.ts:103–111`, `client/src/features/adminOrdersList/AdminOrdersListPagination.tsx:22–28`.

После удаления перечитывается текущий currentPage, но номер страницы не корректируется при уменьшении totalRecord. Backend возвращает запрошенный currentPage и строки по прежнему offset, без переноса на последнюю существующую страницу.

Воспроизведение с текущим recordPerPage=3: есть четыре заказа → перейти на страницу 2 с единственной строкой → удалить её. GET страницы 2 возвращает totalRecord=3 и rows=[], reducer сохраняет currentPage=2, хотя totalPages=1. AdminOrdersListPagination полностью скрывается при totalPages<=1, поэтому нет даже кнопки возврата на страницу 1. Интерфейс показывает пустой список при трёх существующих заказах; изменение фильтра или полная перезагрузка могут восстановить доступ, но обычная пагинация уже недоступна.

Подтверждение: настоящий store и подменённый API с контрактом текущего getForAdmin. После удаления currentPage=2, totalPages=1, ordersList={}. Условие скрытия пагинации проверено по компоненту. Живые записи не удалялись.

Направление исправления: при ответе с сократившимся числом страниц корректировать currentPage до существующей страницы и загружать её с сохранением защиты от устаревших ответов. Для полностью пустой выборки использовать страницу 1.

## R5-3. [P2] ID заказа ошибочно участвует в подборе составных работ как опция

Код: `client/src/features/editOrderForm/ui/CompositeParameterList.tsx:40–49`.

baseOptionIds собирает любое числовое значение из orderValues, включая служебный id заказа и числовые INPUT-поля. В отличие от общего калькулятора и normalizeOrderValues здесь не проверяется, относится ли поле к параметру с опциями. Поэтому order.id, совпавший с ID опции, удовлетворяет ценовому условию, которое пользователь не выбирал.

Воспроизведение на допустимом синтетическом справочнике: редактируется заказ id=12 с car_type=13 (тип B); для составной группы есть работа A с условиями [30,12] и работа B с [31,13]. В baseOptionIds попадают 13 и служебный 12. Кнопка «Добавить» предлагает A как доступную и выбирает её первой, хотя выбран тип B. После «Применить» root normalizer использует только реальные параметры, не находит условие 12 и удаляет операцию. Внешне предложенная операция просто исчезает и добавление не выполняется.

Подтверждение: браузер с настоящим EditOrderForm/CompositeParameterList/normalizeOrderValues. В форме выбран Type B, вложенная модалка предлагает A ONLY, после применения составных операций нет и сумма остаётся 0. Прайс включал собственный mainOptionId в условиях каждой работы, как в проектном формате. Справочник синтетический, соответствие конкретных заказов/цен текущей БД не проверялось.

Направление исправления: собирать базовые опции по метаданным параметров, исключая id, active и INPUT, и использовать одинаковое правило в UI подбора, нормализации и калькуляторе. Наличие служебного поля не должно менять доступность работ.
