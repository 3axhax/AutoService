# Серверное ревью — второй проход

Дата: 2026-11-03. Проверена рабочая копия после исправлений S1–S6. Найдены два P1 и один P2; исходники приложения этим проходом не менялись.

## SR2-1 — P1: недоступный компании параметр сохраняется без проверки и цены

Места: `server/src/orders/orders.service.ts:204–206`, `server/src/price/validate-order-dependencies.ts:45`, `server/src/orderParameters/orderParameters.service.ts:getParameterByName`.

Расчёт и validateOrderDependencies рассматривают только параметры, доступные компании. Но formatter перебирает все ключи тела и ищет каждый параметр в глобальном справочнике по имени, без companyId/allowlist. Поэтому поле, существующее в глобальном справочнике, но отсутствующее в настройках компании, не проверяется валидаторами и при этом превращается в ordersOptionValues. Для неизвестного справочнику поля запись пропускается; проблема именно в существующем, но недоступном параметре. Контроллеры add/edit принимают Record вместо DTO, поэтому whitelist ValidationPipe не ограничивает этот набор полей.

Воспроизведение настоящими PriceService и OrdersService с синтетическими справочниками/repositories: компании доступен только car_type, глобально существует hidden_work с id=99. Запрос hidden_work={30:1} проходит calculateTotalValue с totalValue=0 и доходит до save с опцией parameterId=99/value=30/count=1. Цена опции 30 в синтетическом прайсе присутствует, но расчёт её игнорирует, поскольку параметр не входит в метаданные компании. Реальных записей в БД не выполнялось.

Исправление: единый allowlist параметров компании для валидации, расчёта и преобразования к сохраняемым опциям; отклонять недоступные поля до любой записи. Служебный id редактирования обрабатывать отдельно. Негативные тесты — обычные и составные параметры, существующие глобально, но отключённые у компании, включая компанию без настроенного справочника.

## SR2-2 — P1: закрытие смены не синхронизировано с записью заказа/работы

Места: `server/src/shifts/shifts.service.ts:86–97`, `server/src/orders/orders.service.ts:56–76` и проверка смены перед edit; `server/src/additionalWorks/additionalWorks.service.ts:addNew/edit/delete`.

Новая advisory-блокировка применяется при поиске/создании активной смены. closeAllActiveShiftByUser её не получает, а просто обновляет active/closedAt. Пока заказ уже получил shiftId, но ещё сохраняется, другой запрос может успешно закрыть смену. Затем заказ сохраняется в закрытую смену. При worker edit разрешение по текущей смене проверяется до транзакции и также может устареть к моменту изменения. Дополнительные работы записываются после отдельной транзакции получения смены. Клиентская блокировка действует в одной вкладке и не исключает запрос из другой сессии/вкладки.

Воспроизведение настоящими ShiftsService/OrdersService на изолированных repositories: существующая смена active=true → addNew получает shiftId и останавливается перед фактическим сохранением → closeAllActiveShiftByUser завершает обновление active=false → сохранение продолжается и успешно заканчивается для закрытой смены. В реальной БД эксперимент с записью не проводился. Аналогичные edit/work paths подтверждены чтением кода.

Это оставшийся пробел жизненного цикла, а не повтор дефекта дублей S5. Прежний этап явно ограничивал S5 сериализацией открытия и не гарантировал атомарность закрытия относительно записи из другой сессии.

Исправление: общий протокол транзакционной блокировки закрытия и всех изменений текущей смены; проверку активности и допустимости изменения выполнять внутри защищённой транзакции, сохранять её до завершения записи. Явно определить результат гонки: начатая допустимая запись завершается до закрытия либо поздняя запись отклоняется/относится к новой смене по согласованной политике. Не переносить запись в новую смену молча.

## SR2-3 — P2: отрицательное количество обычной работы проходит валидацию

Места: `server/src/price/validate-order-dependencies.ts:34–39`, `server/src/orders/orders.service.ts:234–240`.

Для SELECT_LIST валидатор фильтрует количества <=0 из набора выбранных опций, но не отклоняет сами значения. Расчёт цены тоже игнорирует отрицательные количества. Formatter затем сохраняет все ключи исходного объекта с Number(count), включая отрицательные. Проверка положительного целого count есть для COMPOSITE_LIST, но отсутствует для обычных количественных опций.

Воспроизведение настоящими PriceService/OrdersService с доступной компанией опцией works/30 и ценой 100: works={30:-2} принимается, totalValue=0, в save передаётся count=-2. Модель count — INTEGER без min-валидации; read-only запрос локальной БД подтвердил 0 CHECK-ограничений у ordersOptionValues. Фактическую отрицательную запись не создавали.

Исправление: валидировать форму SELECT/SELECT_LIST и положительные конечные целые количества до расчёта/formatter. Если UI использует ноль как удаление опции, нормализовать его одинаково во всех этапах либо явно отклонять, но не сохранять запись с нулевым/отрицательным count. Добавить проверки отрицательных, дробных и нечисловых значений; положительные количества должны одинаково участвовать в цене и сохранении.
