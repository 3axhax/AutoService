# Восьмое серверное ревью — 2026-11-03

## SR8-1 — P2: свободный текст используется как ID опции

Место: server/src/orders/orders.model.ts:104–108.

saveOptions определяет необходимость поиска OrderParametersOptions по !isNaN(+option.value), независимо от типа параметра. Нормализация INPUT правильно принимает произвольные строки, но строка Infinity (или 1e309) превращается в числовую Infinity и уходит в WHERE id = Infinity. Sequelize выводит это значение без кавычек, PostgreSQL трактует infinity как имя колонки и возвращает ошибку. В результате допустимое текстовое значение срывает создание/редактирование всего заказа вместо сохранения как текста. Для обычного числового текста также может записаться optionId от чужого параметра при совпадении ID.

Подтверждение: настоящий PriceService.prepareOrder с метаданными INPUT car_make_text принимает строку Infinity; настоящий OrdersService._formatParamToOptions сохраняет её как текст; настоящий Orders.prototype.saveOptions с синтетическими static repositories вызывает findOne с id=Infinity. Настоящий Sequelize PostgreSQL query generator выдаёт SELECT ... WHERE id = Infinity. Синтетический SELECT 1 WHERE 1 = Infinity в локальном PostgreSQL внутри BEGIN READ ONLY подтверждает column "infinity" does not exist. Сессия psql завершилась; реальные заказы/опции не создавались. Полный HTTP создания с рабочей БД не запускался, ошибка запроса и путь до неё подтверждены раздельно.

Рекомендация: определять optionId из метаданных SELECT/SELECT_LIST/COMPOSITE_LIST, а INPUT/GRAPH_INPUT сохранять только как текст без поиска по числовому содержимому. Проверить add/edit, текст Infinity/1e309/числовую строку, отсутствие ложных optionId и сохранение транзакционных hooks. Ограничиться Number.isFinite недостаточно для устранения ложной связи обычного числового текста.

## SR8-2 — P2: экспорт без параметров оставляет HTTP-запрос незавершённым

Место: server/src/orders/orders.service.ts:443–445 и завершение downloadList; OrdersController.downloadList использует @Res().

Ветка формирования/отправки файла выполняется только при parameters.length > 0. Если справочник пуст, метод возвращает null без res.send/res.end и без исключения. Поскольку controller использует @Res(), Nest не отправляет возвращённое значение автоматически. Соединение остаётся открытым, клиент ожидает файл и удерживает pending. Это достижимо, например, у новой компании без companiesParametersOptions: регистрация создаёт компанию, но не её настройки, а OrderParametersService.getAll возвращает parameters=[]. Кнопка Excel на OrdersPage доступна и в таком состоянии.

Подтверждение: изолированный Nest HTTP с настоящими OrdersController/OrdersService и глобальным ValidationPipe, синтетическим авторизованным ADMIN и getAll→parameters=[]. POST /orders/downloadList с filters=[] не получил HTTP-ответ до response timeout 250ms; downloadData не вызван. Воспроизведение запущено внутри локального server-контейнера, на отдельном тестовом listener, без рабочей БД. Таймаут измеряет отсутствие ответа в этом сценарии; по коду отсутствует путь отправки ответа и после этой задержки.

Рекомендация: завершать каждый путь endpoint: отправить корректный файл с базовыми колонками при пустом справочнике либо вернуть явную ошибку/ответ согласованного API. Добавить HTTP-регрессию пустого справочника и проверить снятие клиентского pending после ответа/ошибки.
